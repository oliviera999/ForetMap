### Comportement du runner

`runMigrations` (`database.js`) suit un curseur unique, `schema_version`. Un fichier de numéro
**inférieur** au curseur est **sauté sans erreur** ; il est seulement signalé (`late` dans
`lib/migrationStatus.js`, `skipped` de `deploy_status`). Ce signalement s'appuie sur la table
`schema_migration_files`, qui **n'existe pas encore en prod** (vérifié le 20/11).

Conséquences :

1. les migrations CPT arrivent sur `main` **dans une seule PR** (celle de SI), numérotées sans
   trou au-dessus du dernier numéro de `main` au moment de l'intégration ;
2. un flux intégré **plus tard** que les autres est renuméroté par SI au-dessus de `main` ;
3. si une autre PR prend `374` avant SI, SI décale toute la série. Le réglage GitHub « Require
   branches to be up to date before merging » reste la garde décisive.

**Rendre la renumérotation gratuite** (obligatoire pour F1, F2, F5) :

- le numéro n'apparaît **que** dans le nom du fichier de migration ;
- les tests retrouvent le fichier par son suffixe (`/_contenus_terrain_2026_11_20\.sql$/`),
  jamais par son numéro, et leur propre nom ne porte pas de numéro
  (`tests/content/contenus-terrain-2026-11-20.test.js`, pas `migration-374-…`) ;
- ni le code, ni la doc, ni `changelog.d/` ne citent le numéro : écrire « migration
  `contenus_terrain_2026_11_20` ».

Une migration de flux ne dépend d'aucune autre migration de flux. Vérifié pour les trois :

## 3. Carte de propriété des fichiers

Règles communes :

- un flux ne modifie **que** les fichiers de sa liste. Un fichier absent de toutes les listes
  est réservé à SI ;
- **nouveaux tests dans de nouveaux fichiers**, préfixés par le domaine du flux. Un fichier de
  test existant n'appartient qu'au flux qui possède le module testé ;
- les miroirs `lib/shared/*.js` ne s'éditent pas à la main : modifier la source `src/shared/…`
  puis `npm run sync:shared-cores` (le miroir généré appartient au flux de sa source) ;
- styles : jamais `src/index.css`. Chaque flux écrit dans une feuille de son domaine, importée
  par son composant (patron : `src/components/observations/speciesObservations.css`) ;
- ouvrir un tutoriel depuis un écran : **importer** `src/components/TutorialPreviewModal.jsx`
  sans le modifier (F2 et F3 en ont besoin tous les deux) ;
- `docs/API.md`, `docs/MCP.md`, `docs/reference/` : sections du domaine seulement, sans
  reformater le reste.

## 8. Ordre de fusion pour SI

1. `git fetch`, relever le dernier numéro de migration de `origin/main` (`M`).
2. Fusionner dans `integration/cpt`, dans cet ordre : **F1, F2, F5** (flux à migration), puis
   **F3, F4** (sans migration, ordre libre). Un flux absent est simplement omis.
3. Après chaque fusion d'un flux à migration : `git mv` de son fichier vers `M+1`, `M+2`, `M+3`
   dans l'ordre de fusion, puis `node --test tests/migrations-numbering.test.js tests/migrations-unique-numbers.test.js`.
4. Mettre à jour `sql/schema_foretmap.sql`, traiter les besoins hors périmètre (shell,
   `routes/tutorials.js`, lectures de `quiz_question_species` dans le connecteur, tests MCP
   partagés), reporter `changelog.d/`.
5. Rejouer deux fois la série complète sur base fraîche, dans l'ordre réel.
6. Juste avant d'ouvrir la PR vers `main` : `git fetch` à nouveau. Si `main` a dépassé `M`,
   renuméroter toute la série au-dessus.
7. Un flux qui arrive **après** la fusion de la PR de SI part dans une PR à lui, numéroté
   au-dessus du `main` du jour.
8. **F6 ne passe pas par SI** : PR autonome vers `main`, dès qu'elle est prête. Si elle est

9. **F7 vient après SI** : S0 relancée, puis une PR à lui, sa migration numérotée au-dessus du
